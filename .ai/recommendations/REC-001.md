# Broken first migration leaks a disposable test database

**Finding:** REVIEW-001-01-A — a broken first migration leaves an orphaned `grademate_test_*` database, because `pytest_configure` only records the name to clean up after the upgrade succeeds.
**Agrees with the finding:** Yes
**Should be corrected:** Yes, in the reviewed task
**Code change:** Yes — see task draft below
**Suggested tasks:** None — fix goes into TASK-001 itself, not a new task

Verified directly — `pytest_configure` in `tests/conftest.py` records `_state["test_db_name"]` only after `command.upgrade(alembic_cfg, "head")` succeeds, so a failed upgrade skips the write and `pytest_unconfigure` finds nothing to drop.
Reproduced the same shape in an isolated conftest to confirm pytest still calls `pytest_unconfigure` after `pytest_configure` raises.
`HEAD` moved one commit past `reviewed_commit`, adding only the review file itself, so the finding still applies unmodified.
Agreed, and correctable inside TASK-001 — a deterministic leak, not data loss, MEDIUM severity as scored.

#### Task draft: Record the disposable test database before running migrations

**Objective:** A broken first migration must not leave an orphaned `grademate_test_*` database on the Postgres server.

**Requirements:**
* `tests/conftest.py`, `pytest_configure`: write `_state["test_db_name"]` and the admin connection info immediately after `CREATE DATABASE` succeeds — before the `command.upgrade(alembic_cfg, "head")` call runs, not after.

**Acceptance Criteria:**
* A deliberately broken migration revision (raising during `upgrade head`) leaves no `grademate_test_*` database behind after the test session ends.
* The existing successful-run behavior (create, migrate, drop) is unchanged.
